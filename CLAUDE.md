# Expenser Web App

A weekly/monthly expense tracker for managing personal budgets in Argentine Pesos (ARS), with
per-user accounts. TypeScript monorepo: a Fastify + Drizzle backend and an Astro webapp.

## Monorepo Structure

**Package manager:** pnpm >= 10 | **Orchestration:** Turborepo | **Node:** >= 22.12.0

```
expenser/
├── apps/
│   ├── backend/    # REST API + MCP server: Fastify + Drizzle ORM over libSQL (SQLite locally, Turso in prod)
│   └── webapp/     # Astro + React + Tailwind CSS (installable PWA)
├── deploy/         # Droplet deploy: deploy.sh, pm2 ecosystem.config.cjs, nginx/ server blocks
├── turbo.json
├── pnpm-workspace.yaml
└── package.json
```

## Backend (`apps/backend`)

**Stack:** TypeScript (ESM, strict) on Node 22, Fastify 5 (`@fastify/cors`, `@fastify/cookie`),
Drizzle ORM 0.45 + drizzle-kit over `@libsql/client` (a local SQLite file or remote Turso), zod 4,
bcrypt, the MCP TypeScript SDK v2 (`@modelcontextprotocol/server`)

- Dev: `tsx watch src/server.ts` (what `pnpm dev` runs)
- Build: `tsc -p tsconfig.build.json` → `dist/` (mirrors `src/`); `pnpm start` runs `dist/server.js`
- Server runs on `http://localhost:3001` (`PORT`/`HOST` env; pm2 binds `127.0.0.1` in production)
- Before committing: `pnpm typecheck` and `pnpm test` (in `apps/backend`)

### Feature pattern

Each feature is a module: a service with its zod body schemas and functions (context first), and a
controller that's a Fastify plugin built from the `Context`.

```typescript
// categories.service.ts
export type Category = typeof categories.$inferSelect // { id, name, color, userId }
export const createCategoryBody = z.object({ name: z.string(), color: z.string() })

export async function addCategory(ctx: Context, userId: number, body: z.output<typeof createCategoryBody>) {
  // every query is scoped by the user's id
  return one(await ctx.db.insert(categories).values({ ...body, userId }).returning())
}

// categories.controller.ts
export function categoriesController(ctx: Context): FastifyPluginAsync {
  return async (app) => {
    app.post('/categories', async (req, reply) => {
      const user = await requireUser(ctx, req) // 401 without a session or API key
      const category = await addCategory(ctx, user.id, parse(createCategoryBody, req.body))
      reply.status(201)
      return category
    })
  }
}
```

- Register a new feature's controller in `buildApp()` in `src/app.ts`.
- When the MCP server offers an action too, its logic lives in the service function the route
  calls (`addExpense`, `editCategory`, `updateProfile`, …): body in, row or `AppError` out. The MCP
  tool calls the same function, so both validate identically.
- Errors: throw `AppError.badRequest` / `notFound` / `new AppError(status, msg)`; anything else
  becomes a logged 500. Every error body is `{ "message": "..." }`, including malformed JSON (Fastify's
  parser errors), zod failures (`parse()`: `field: problem`) and non-numeric ids (`parseId`, 400
  `Invalid id`). Unknown routes are 404 `Route not found`.
- Bodies are validated with zod (`parse(schema, req.body)`); unknown fields are dropped. Optional
  fields are `.nullish()` (an explicit null means "not given", as clients often send it); normalize
  with `given()`. PATCH services pass only the given fields to `.set()` (Drizzle skips `undefined`)
  and use `.returning()` to get the row back; "not found" is an empty `returning()` / select.
- Tables are exported plural (`users`, `expenses`, …) so rows can be singular. DB columns are
  camelCase, the same as the TS keys and the JSON fields, so rows are returned as they are. Select
  `userColumns` (auth.service) to get a `User` from a join.
- Time: use `ctx.now()`, never `new Date()`, in services, so tests can fix the clock. Timestamp
  columns are `Date`s in TS; the custom column type stores them with `encodeTimestamp` (and Drizzle
  applies it to query parameters compared with those columns too). JSON serializes them with
  `toISOString()`.
- `ctx.db` is one Drizzle instance over one libSQL client for the whole process. Outside
  transactions, the client sends each statement to Turso as its own HTTP pipeline that opens and
  closes its stream, so nothing can expire between requests (see `db.test.ts`). Use
  `ctx.db.transaction()` for multi-statement writes (see signup); don't retry writes after
  transport errors.
- bcrypt's async API runs on libuv's thread pool, off the event loop.

### Authentication

Session-based auth using an httpOnly cookie (`session_id`), not JWTs, plus per-user **API keys**
for scripts (`Authorization: Bearer exp_...`).

- `requireUser` and `requireSessionUser` (`lib/auth.ts`) read the `session_id` cookie and load the
  session + user; with no valid session they fall back to a Bearer API key. Each request is
  authenticated at most once. Nothing is rejected globally: handlers opt in by calling one of them.
- `requireUser` 401s without a user and accepts both auth methods. Every route except `/health`,
  signup, login, the `api-keys` routes and `/mcp` uses it.
- `/mcp` accepts an OAuth access token (`accessTokenUser`, oauth.service) or an API key
  (`bearerApiKeyUser`), never the session cookie, so a web page can't drive it through a logged-in
  browser. It 401s with `WWW-Authenticate: Bearer resource_metadata="…"` (see OAuth below).
  OAuth access tokens work on `/mcp` only, not on the REST routes.
- `requireSessionUser` additionally 403s API-key requests. The `api-keys` routes use it, so a leaked
  key can't create or revoke keys.
- API keys: `exp_` + 32 random bytes (base64url). Only a SHA-256 hash (`keyHash`, unique, used for
  lookup) and a display `prefix` are stored; the full key is returned once by `POST /api-keys`.
  Revoking deletes the row. `lastUsedAt` is updated at most once a minute per key. Max 10 per user.
- Sessions live in the `Session` table (30-day expiry, cookie `Max-Age` to match), created on
  signup/login, deleted on logout or lazily when an expired one is used.
- Passwords are hashed with bcrypt (cost 10, `$2b$`, compatible with every previous backend's
  hashes). Signup validates name/email/password/allowance and seeds 5 starter categories (Food,
  Transport, Entertainment, Bills, Other) for the new user in the same transaction.
- Cookie flags (`SESSION_COOKIE_SECURE`, `SESSION_COOKIE_SAMESITE`) come from `Config` — set
  `secure=true` and `sameSite=none` when the API and webapp are on different origins in production.

| GET | `/.well-known/oauth-authorization-server` | — | Authorization server metadata (RFC 8414) |
| POST | `/oauth/register` | — | Dynamic client registration (RFC 7591); clients are public |
| GET | `/oauth/authorize` | — | Checks the request, forwards it to the webapp's `/authorize` (303) |
| GET / POST | `/oauth/consent?<authorize query>` | session only | Consent page: who's asking / decide (`{ approve }` → `{ redirectTo }`) |
| POST | `/oauth/token` | — | Form-encoded: `authorization_code` (PKCE) or `refresh_token` grant |

| DELETE | `/oauth/connections/{id}` | session only | Revoke a connection (204) |

"Required" accepts a session cookie or an API key; "session only" rejects API keys with 403.

**Weekly/monthly summary (`summarize` in `expenses.service.ts`):**
- Weeks run **Saturday through Friday** (see `weekStart` in `lib/dates.ts`), in the server's local
  time zone (`TZ`).
  Optional `weekStart` selects a previous Saturday; future weeks are rejected. Responses include
  `currentWeekStart` and `today`; summary expenses include a calendar `date` for consistent editing
  across browser/server time zones. Queries are bounded by both ends of the selected week.
- The home screen supports previous/next-week navigation and adding, editing or deleting expenses
  in the selected week. Optional `date` on POST/PATCH sets `createdAt` (the existing expense date);
  omitting it preserves the current-time default on creation and the original date on updates.
  Dates must be valid calendar dates on or before today. Saved categories can be kept even if deleted.
- The allowance is **per-user**: `User.expendableAmountPerWeek`, set at signup and editable via
  `PATCH /auth/me`. There is no hardcoded global allowance.
- The response also includes a `monthly` block (calendar month to date): allowance is derived as
  `(weekly allowance / 7) * daysInMonth`, spent is aggregated from expenses in the current month.

### MCP server (`modules/mcp`)

`/mcp` lets AI assistants use the app through tools (Claude apps: a custom connector with URL
`<api>/mcp`, signing in with OAuth; Claude Code: `claude mcp add --transport http expenser
<api>/mcp`, then OAuth via `claude mcp login`, or `--header "Authorization: Bearer exp_..."`): `get_summary`,
`list_expenses`, `add_expense`/`update_expense`/`delete_expense`, `list_categories`/`add_category`/
`update_category`/`delete_category`, `get_profile`/`update_profile`.

- Built on the MCP TypeScript SDK v2's Streamable HTTP support, stateless (no MCP sessions) with JSON
  responses. `mcp.controller.ts` authenticates the bearer token (OAuth access token or API key),
  then serves the request with a fresh `McpServer` from `buildMcpServer(ctx, user)`, so tools act as
  the token's owner. 2026-07-28 requests (protocol version in each request's `_meta`) go to the
  SDK's `createMcpHandler` (`legacy: 'reject'`), which gets the user through `authInfo.extra`;
  2025-era requests (`isLegacyRequest`: `initialize` first, no envelope) go to a
  `WebStandardStreamableHTTPServerTransport` with `enableJsonResponse`, and their GET/DELETE get 405.
  The route bridges Fastify and the SDK's web `Request`/`Response`; the plugin keeps bodies raw
  (a `*` string parser) so the SDK parses and validates them itself.
- A tool is a `server.registerTool(name, { description, inputSchema: z.object(…), annotations },
  handler)` call in `buildMcpServer`: field `.describe()`s document the input schema, and
  `annotations: { readOnlyHint: true }` / `{ destructiveHint: false }` mark reads and pure additions.
  Optional arguments are `.nullish()`: models often send null for what they leave out.
- Tools return `reply(tool, work)`: the value as JSON text, an `AppError` as a tool error
  (`isError`) the model reads and can act on, anything else as a logged `isError` "Internal Server
  Error". The SDK turns invalid arguments into tool errors too.
- Tools take categories by name (case-insensitive) and return expenses with their local `date`.
  `list_expenses` is MCP-only: date range/category/description filters, totals over every match,
  at most `limit` expenses.
- The server declares `tools.listChanged: false` (the tools never change), so clients don't open
  `subscriptions/listen` streams. No Host/Origin validation: it protects servers that trust whoever
  can reach them, and this one trusts only bearer tokens.

### OAuth (`modules/oauth`)

How the Claude apps connect to `/mcp`, following Claude's requirements for remote MCP servers:

1. `/mcp` 401s with `resource_metadata` → `/.well-known/oauth-protected-resource/mcp` (`resource`
   = `{API_URL}/mcp`) → `/.well-known/oauth-authorization-server` (issuer = `API_URL`).
2. The client registers (`/oauth/register`, DCR): https or loopback http redirect URIs only. Every
   client is public (`token_endpoint_auth_method: none`); there's no CIMD support, so in Claude's
   connector dialog users pick "Register automatically".
3. `GET /oauth/authorize` checks the client and redirect URI (errors → 400 for the user), then the
   rest (`response_type=code`, PKCE S256, `resource`; errors → redirect to the client with `error`
   and `state`), and 303s valid requests to `{WEBAPP_URL}/authorize?<same query>`.
4. The webapp's consent page passes that query to `/oauth/consent` (session only, so API keys
   can't grant access): GET shows the client name and redirect URI; POST `{ approve }` returns the
   client's redirect URI with a `code` (10 min, single use: `DELETE … RETURNING`) or
   `error=access_denied`, plus `state`.
5. `POST /oauth/token` (form-encoded, RFC 6749 `{ error, error_description }` errors, repeated
   parameters rejected) exchanges the code (client, redirect URI and PKCE verifier must match) for an
   access token (`exa_`, 1 hour) and a refresh token (`exr_`, 90 days). A refresh rotates both in
   one `UPDATE`, so each refresh token works once.

- `register` and `token` live in their own plugin scope (`protocolEndpoints`): raw bodies, and an
  error handler that answers `OAuthError`s (and parse errors) in the RFC 6749 shape.
- Loopback redirect URIs match on any port (RFC 8252), for Claude Code's per-run callback port.
- A grant (`OAuthGrant` row) is one connection: it holds the current token hashes. Settings lists
  them (`/oauth/connections`) and disconnecting deletes the row, invalidating both tokens.
- Expired codes and grants are deleted when new ones are created.

### Auth flow

- No route guarding at the Astro/SSG level (the site is static) — each protected renderer uses
  `useAuth()` (or an inline `getCurrentUser()` check on `/login` and `/signup`) and redirects via
  `window.location.href`.
- `useAuth()` paints the last-known user from `localStorage` (via `cache.ts`) immediately, then
  calls `GET /auth/me` to revalidate. On a confirmed 401 it clears the cache and redirects to
  `/login?next=<current page>`; on a network error it keeps showing the cached user if there is one.
- Login and signup go to `?next=` afterwards (same-origin only, see `lib/next.ts`), so the OAuth
  consent page survives a login.
- `Header`'s logout button calls `POST /auth/logout`, clears the cache, and redirects to `/login`.

## Deployment

Both apps run on a single **DigitalOcean droplet**; the database is on **Turso** (hosted libSQL).
Manual deploys only, no CI/CD. Everything lives in `deploy/`:

- `deploy/deploy.sh` runs on the droplet: `git pull`, `pnpm install`, builds the backend (`tsc`)
  and webapp (astro) per-package (not via turbo, whose cache doesn't see the gitignored `.env`
  files), `rsync`s `apps/webapp/dist/` to `/var/www/expenser`, then `pm2 delete` + `pm2 start` (so
  pm2 config changes always apply) + `pm2 save`.
- `deploy/ecosystem.config.cjs`: pm2 app `expenser-backend` runs `apps/backend/dist/server.js`
  (`--enable-source-maps`), which reads `apps/backend/.env` itself; `HOST=127.0.0.1`.
- `deploy/nginx/expenser.conf` serves the static site (`/_astro/` immutable, everything else
  `no-cache` for PWA updates). `deploy/nginx/expenser-api.conf` proxies
  `expenser-api.juanromerodev.com` → `127.0.0.1:3001`. TLS is added by `certbot --nginx`.
- Redeploy: on the droplet, `cd ~/expenser && pnpm run deploy` (not bare `pnpm deploy`, a pnpm built-in).
- Backend env vars live in `apps/backend/.env` on the droplet: edit it, then
  `pm2 restart expenser-backend`.
- Schema changes: edit `apps/backend/src/db/schema.ts`, run `pnpm --filter @expenser/backend
  db:generate`, review and commit the new `drizzle/` SQL file (and its `meta/` snapshot). The
  backend applies pending migrations at startup, locally and on Turso alike, and records them in
  `__drizzle_migrations`. Never edit a migration that has been applied. (`_migrations` is the Rust
  backend's record; it's left alone.)

## Database Schema

Source of truth: `apps/backend/src/db/schema.ts` (Drizzle), with migrations in `apps/backend/drizzle/`.
The tables are the ones the original Prisma backend created (PascalCase tables, camelCase columns,
Prisma's constraint and index names); `0000_baseline.sql` adopts them.

```
User     (id PK, name, email UNIQUE, passwordHash, expendableAmountPerWeek REAL,
          role DEFAULT 'user', createdAt, updatedAt)
Session  (id TEXT PK, userId → User, expiresAt, createdAt)
Category (id PK, name, color, userId → User)
Expense  (id PK, description, amount REAL, category TEXT, createdAt, updatedAt, userId → User)
ApiKey   (id PK, name, prefix, keyHash UNIQUE, lastUsedAt NULL, createdAt, userId → User)
OAuthClient (id TEXT PK, name, redirectUris (JSON array), createdAt)
OAuthCode   (codeHash PK, clientId → OAuthClient, userId → User, redirectUri, codeChallenge, expiresAt)
OAuthGrant  (id PK, clientId → OAuthClient, userId → User, accessTokenHash UNIQUE, accessExpiresAt,
             refreshTokenHash UNIQUE, refreshExpiresAt, lastUsedAt NULL, createdAt)
```

**Design notes:**
- Timestamps are UTC `TEXT` in a fixed-width format, `2026-10-12T03:00:00.000+00:00` (what Prisma
  wrote), so range queries compare them as strings: the `timestamp` column type writes them with
  `encodeTimestamp()`, and raw SQL must too. The API returns them as `2026-10-12T03:00:00.000Z`.
- `Expense.category` stores the category name as a string (no foreign key to `Category`). The
  handler resolves `categoryId` → `category.name` at write time. Deleting a category does not
  affect existing expenses.
- `Expense.createdAt` is when the expense happened: now by default, or the start of the local day
  given as `date`.
- Every `Category`/`Expense`/`Session`/`ApiKey` row is scoped to a `User` via `userId` with
  `ON DELETE CASCADE`.

## Conventions

- **TypeScript (backend):** strict + `noUncheckedIndexedAccess`, ESM with `.js` import
  specifiers (NodeNext), `verbatimModuleSyntax` (so `import type` where possible). Services throw
  `AppError` for expected failures; no non-null assertions on query results (`one()` for rows that
  must exist, `const [row] = …` + a check otherwise). Tests go in `tests/*.test.ts` (`node:test`),
  driving the real app through `TestApp` (`app.inject`).
- **TypeScript (webapp):** strict mode, extends `astro/tsconfigs/strict`, `jsx: react-jsx` (no
  explicit React import needed). Use `type` imports where possible (`import type { ... }`).
