# Expenser

A weekly expense tracker for managing personal budgets in Argentine Pesos (ARS).

## Monorepo Structure

This is a [Turborepo](https://turbo.build) + [pnpm workspaces](https://pnpm.io/workspaces) monorepo.

```
expenser/
├── apps/
│   ├── webapp/          # Astro + React + Tailwind frontend
│   └── backend/         # Fastify + Drizzle ORM (libSQL) REST API and MCP server
├── deploy/             # Droplet deploy script, pm2 config, nginx server blocks
├── package.json         # Root scripts and workspace config
├── pnpm-workspace.yaml
└── turbo.json
```

## Requirements

- Node.js >= 22.12.0
- pnpm >= 10

## Getting Started

Install all dependencies from the root:

```sh
pnpm install
```

Run all apps in development mode:

```sh
pnpm dev
```

Or run a specific app:

```sh
pnpm --filter @expenser/webapp dev
pnpm --filter @expenser/backend dev
```

## apps/webapp

**Stack:** Astro 6, React 19, Tailwind CSS 4

A client-side expense tracker that runs entirely in the browser. Data is persisted in `localStorage`.

### Features

- Weekly budget of 100,000 ARS (configurable)
- Carry-over logic: leftover or overspent balance rolls into the next week
- Expense categories with color badges (configurable)
- Browse previous Saturday-to-Friday weeks and return to the current week
- Add missed expenses and edit or delete expenses in the selected week
- Settings screen to manage allowance and categories
- Connect Claude (Settings → Connected apps) to read and manage expenses by chatting

## apps/backend

**Stack:** TypeScript on Node.js, [Fastify](https://fastify.dev) 5, [Drizzle ORM](https://orm.drizzle.team)
over [libSQL](https://github.com/tursodatabase/libsql-client-ts): a SQLite file locally,
[Turso](https://turso.tech) (hosted libSQL) in production. [zod](https://zod.dev) validates request
bodies and MCP tool input.

A REST API with one module per feature: a controller (the Fastify routes) and a service (the logic
and its queries).

### Structure

```
apps/backend/
├── drizzle/                 # Migrations, generated by drizzle-kit and applied at startup
│   ├── 0000_baseline.sql    # The schema the previous backends created (adopted as it is)
│   └── meta/                # drizzle-kit's snapshots and journal
├── drizzle.config.ts        # drizzle-kit: schema path, migrations folder, database
├── src/
│   ├── server.ts            # Entry point: .env, config, database, server, graceful shutdown
│   ├── app.ts               # buildApp(): CORS, cookies, correlation ids, error bodies, routes
│   ├── context.ts           # Context { db, config, now } that handlers and services run with
│   ├── config.ts            # Environment variables, validated at startup
│   ├── db/
│   │   ├── schema.ts        # Drizzle tables (and the timestamp column encoding)
│   │   └── index.ts         # openDatabase(): libSQL client + Drizzle + migrations
│   ├── lib/
│   │   ├── auth.ts          # requireUser / requireSessionUser: session cookie or API key
│   │   ├── errors.ts        # AppError ({ "message" } error bodies), parse() (zod), parseId()
│   │   ├── dates.ts         # Saturday–Friday weeks and months, in the server's time zone
│   │   ├── tokens.ts        # Random secrets (API keys, OAuth tokens) and their stored hashes
│   │   └── logger.ts        # One colored line per request; details of every 5xx
│   └── modules/
│       ├── auth/            # /auth/*: signup, login, logout, profile; sessions
│       ├── api-keys/        # /api-keys, API key authentication
│       ├── categories/      # /categories
│       ├── expenses/        # /expenses, weekly/monthly summary
│       ├── mcp/             # /mcp: MCP server for AI assistants such as Claude
│       └── oauth/           # OAuth for /mcp: discovery, registration, consent, tokens, connections
├── tests/                   # API tests against the real app and a temporary database
└── .env.example
```

### Architecture

- `buildApp(ctx)` registers one Fastify plugin per feature. Handlers get the `Context` (database,
  config, and `now()`, which tests fix) by closure.
- Authentication is opt-in per route: a handler calls `requireUser(ctx, req)` (session cookie or API
  key, else 401) or `requireSessionUser(ctx, req)` (session only; 403 for API keys) and gets the user.
- Queries go through Drizzle's query builder (`ctx.db.select().from(expenses).where(…)`), typed from
  `src/db/schema.ts`. Every query is scoped by the user's id.
- Errors are `AppError`s: expected ones carry a status and message; anything else is logged and
  answered with a 500. Every error body is `{ "message": "..." }`.
- Actions the MCP server also offers (adding an expense, editing a category, …) live in service
  functions such as `addExpense`, which the REST route and the MCP tool both call, so they
  validate the same way.
- One libSQL client serves every request: outside transactions it sends each statement to Turso as
  its own HTTP request, opening and closing its stream in it, so no stream can expire between
  requests.

To add a feature, create `src/modules/<name>/` with a controller and a service, and register the
controller in `buildApp()` (`src/app.ts`).

### MCP server

`/mcp` is a [Model Context Protocol](https://modelcontextprotocol.io) server, so AI assistants such
as Claude can read and manage your expenses. It speaks MCP's Streamable HTTP transport through the
official [TypeScript SDK](https://ts.sdk.modelcontextprotocol.io/v2/) (v2), without sessions:
2026-07-28 clients and 2025-era ones alike. Clients sign in with OAuth, or send an API key.

| Tool | Description |
| :--- | :--- |
| `get_summary` | The current (or a past `weekStart`) week's balance and the month to date, with today's date |
| `list_expenses` | Search by date range, category and description: count, total and per-category totals of every match, plus the newest `limit` (default 100) |
| `add_expense`, `update_expense`, `delete_expense` | Categories are given by name, ignoring case |
| `list_categories`, `add_category`, `update_category`, `delete_category` | |
| `get_profile`, `update_profile` | Name and weekly allowance |

**Claude apps (web, desktop, mobile):** in Claude, go to **Customize → Connectors → Add custom
connector** and enter `https://expenser-api.juanromerodev.com/mcp`. If it asks how Claude should
register, choose **Register automatically**. Claude then opens Expenser, where you log in and
approve the connection. It appears under **Settings → Connected apps**, where you can disconnect it.

**[Claude Code](https://code.claude.com):** the same OAuth sign-in, through your browser:

```sh
claude mcp add --transport http expenser https://expenser-api.juanromerodev.com/mcp
claude mcp login expenser
```

Or skip OAuth with an API key from Settings (`--header "Authorization: Bearer exp_..."`). Locally,
the URL is `http://localhost:3001/mcp`.

The OAuth side (`modules/oauth`) follows what Claude expects of a remote MCP server: protected
resource and authorization server metadata under `/.well-known/`, dynamic client registration, the
authorization code flow with PKCE (S256), and rotating refresh tokens. `/oauth/authorize` forwards
valid requests to the webapp's `/authorize` page, where the logged-in user approves or denies them.
Access tokens (`exa_…`, 1 hour) only work on `/mcp`; refresh tokens (`exr_…`) last 90 days from
their last use.

### Database

The schema is [`src/db/schema.ts`](apps/backend/src/db/schema.ts). To change it, edit the schema and
generate the migration:

```sh
pnpm --filter @expenser/backend db:generate
```

That writes the next SQL file to [`drizzle/`](apps/backend/drizzle) (review and commit it). Pending
migrations are applied automatically when the server starts, to the local file and to Turso alike,
and recorded in the `__drizzle_migrations` table. Never edit a migration that has been applied.
`pnpm db:studio` opens [Drizzle Studio](https://orm.drizzle.team/drizzle-studio/overview) on the
database in `.env`.

The baseline migration is the schema the Prisma and then the Rust backend created, with
`IF NOT EXISTS`, so existing databases (like production) are adopted as they are. Timestamps are
stored as UTC text in the format Prisma used (`2026-10-12T03:00:00.000+00:00`).

### Environment Variables

The defaults work for local development. To override them, copy `.env.example` to `.env`:

```sh
cp apps/backend/.env.example apps/backend/.env
```

| Variable | Default | Description |
| :--- | :--- | :--- |
| `TURSO_DATABASE_URL` | `file:./dev.db` | A local SQLite file (created on first start), or in production a `libsql://…turso.io` URL |
| `TURSO_AUTH_TOKEN` | — | Turso auth token. Required only for remote (`libsql://`) databases |
| `PORT` | `3001` | Port the server listens on |
| `HOST` | `0.0.0.0` | Interface to bind. pm2 sets `127.0.0.1` in production so only nginx can reach it |
| `API_URL` | `http://localhost:<PORT>` | The API's public URL: the OAuth issuer and the base of the MCP server's URL. Set it in production |
| `WEBAPP_URL` | `http://localhost:4321` | Allowed CORS origin (the frontend URL), and where OAuth consent happens |
| `SESSION_COOKIE_SECURE` | `false` | Set `true` in production so session cookies require HTTPS |
| `SESSION_COOKIE_SAMESITE` | `lax` | Cookie `SameSite` policy. `lax` works for `expenser.*` + `expenser-api.*` (same site); `none` only if they're on different sites |

Weeks and months follow the server's local time zone (`TZ`).

## Deployment

Both apps run on a single **DigitalOcean droplet**, with the database on **Turso**. Deploys are manual
(no CI/CD): SSH into the droplet and run the deploy script.

| Piece | How it runs | URL |
| :--- | :--- | :--- |
| Webapp | Static Astro build in `/var/www/expenser`, served by nginx | `https://expenser.juanromerodev.com` |
| Backend | Node.js (Fastify) under **pm2** on `127.0.0.1:3001`, reverse-proxied by nginx | `https://expenser-api.juanromerodev.com` |
| Database | Turso DB `expenser` (libSQL) | — |

Everything lives in [`deploy/`](deploy):

- [`deploy/deploy.sh`](deploy/deploy.sh) pulls, installs, builds both apps, `rsync`s the webapp to the web root, and restarts the backend under pm2
- [`deploy/ecosystem.config.cjs`](deploy/ecosystem.config.cjs) is the pm2 process definition (the server loads `apps/backend/.env` itself)
- [`deploy/nginx/`](deploy/nginx) has one server block per domain

### One-time droplet setup

```sh
# System packages (Ubuntu)
sudo apt update && sudo apt install -y nginx certbot python3-certbot-nginx rsync git
# Node 22+ (e.g. via nvm or NodeSource), then pnpm + pm2
corepack enable && corepack prepare pnpm@10 --activate
npm install -g pm2

# Firewall: only SSH + HTTP(S)
sudo ufw allow OpenSSH && sudo ufw allow 'Nginx Full' && sudo ufw enable

# Code + web root (owned by the deploy user so deploy.sh can write without sudo)
git clone git@github.com:juanrm7/expenser.git ~/expenser && cd ~/expenser
sudo mkdir -p /var/www/expenser && sudo chown "$USER" /var/www/expenser

# Production env files (gitignored)
cp apps/backend/.env.example apps/backend/.env   # then edit, see below
echo 'PUBLIC_BACKEND_URL=https://expenser-api.juanromerodev.com' > apps/webapp/.env
```

Production `apps/backend/.env`:

```sh
TURSO_DATABASE_URL=libsql://<db>-<org>.turso.io
TURSO_AUTH_TOKEN=<turso db tokens create expenser>
PORT=3001
API_URL=https://expenser-api.juanromerodev.com
WEBAPP_URL=https://expenser.juanromerodev.com
SESSION_COOKIE_SECURE=true
SESSION_COOKIE_SAMESITE=lax
```

nginx + TLS:

```sh
sudo cp deploy/nginx/expenser.conf deploy/nginx/expenser-api.conf /etc/nginx/sites-available/
sudo ln -s /etc/nginx/sites-available/expenser.conf /etc/nginx/sites-enabled/
sudo ln -s /etc/nginx/sites-available/expenser-api.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
# After DNS points at the droplet:
sudo certbot --nginx -d expenser.juanromerodev.com -d expenser-api.juanromerodev.com
```

First deploy, then make pm2 survive reboots:

```sh
pnpm run deploy
pm2 startup   # prints a sudo command, run it
pm2 save
```

**DNS:** in DigitalOcean → Networking → Domains → `juanromerodev.com`, point the `expenser` and
`expenser-api` **A** records at the droplet's IP.

### Redeploy (the common case)

```sh
ssh <droplet> 'cd ~/expenser && pnpm run deploy'
```

(Use `run deploy`, not `deploy`, since bare `pnpm deploy` is a built-in pnpm command.) Set `BRANCH=...`
to deploy something other than `main`, or `WEB_ROOT=...` for a different nginx root.

Database migrations are applied when the backend starts.

To change backend env vars, edit `apps/backend/.env` and run `pm2 restart expenser-backend` (the
server reads the file at startup). Changing `apps/webapp/.env` requires a redeploy, because the
values are baked into the build. Logs: `pm2 logs expenser-backend`.

### Switching from the Rust backend (one-time)

The usual `pnpm run deploy` does it. The deploy script that runs is the Rust-era one, but it pulls
first and then uses the new build script (`tsc`) and pm2 config, deleting the pm2 process and
starting it again on Node. Rust must still be installed for that run, since the old script checks
for cargo.

The production `.env` needs no changes (`RUST_LOG`, if set, is ignored), and the database is adopted
as it is: on first start the backend records the baseline migration in `__drizzle_migrations`, which
changes nothing else. The Rust backend's `_migrations` table is left in place, so the previous
backend could still run against the database. Afterwards `apps/backend/target/` can be deleted, and
Rust uninstalled (`rustup self uninstall`) along with the swap file if nothing else needs them.
